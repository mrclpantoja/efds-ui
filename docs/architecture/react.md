# @efds-ui/react — convenções

O React não tem identidade visual: cada componente monta `className` com as classes `.eds-*` do core e define atributos HTML/ARIA. Sem CSS, sem `style`, sem dependência de runtime além de `react` (peer) e do `@efds-ui/behavior`, usado **só** pelo subcaminho `@efds-ui/behavior/export` (geradores de arquivo da exportação). Contrato de markup: CSS em `packages/core/src/**` e `apps/playground/src/demos/*.tsx`; obrigações de comportamento: `comportamento.md`.

## Estrutura

```
packages/react/src/
  index.ts                  reexport nomeado (componentes + tipos)
  utils/cx.ts
  internal/                 privado, nunca exportado: Glyph/glyphs (fechar, chevrons, setas, check), tipos de layout
  components/<Nome>/
    <Nome>.tsx  <Nome>.test.tsx  index.ts
```

Ícones públicos ficam em `@efds-ui/icons` (que só tem `react` como peer; `@efds-ui/react` não depende dele). Glifos que um componente precisa por dentro (fechar do Modal, chevron do Select/Pagination, setas de ordenação) saem de `internal/glyphs.tsx`.

## Convenções de props

- Mesmo vocabulário do core: `variant="primary"` ⇄ `.eds-button-primary`. Unions de string literais, sem `enum`, sem `any`.
- Só props semânticas (`variant`, `size`, `loading`, `invalid`, `gap`, `span`...). Nunca aparência (`color`, `radius`, `padding`, `style`).
- Estender os atributos nativos do elemento raiz; `className` é mesclado por `cx` (classes do core primeiro, a do consumidor por último); `...rest` vem **antes** das props controladas (o componente não deixa o consumidor desfazer `aria-busy`, `role`, `type`).
- `forwardRef` + `displayName` (compatível com React 18 e 19, conforme o peer). Quando migrarmos o peer para 19, troca-se por `ref` como prop em todos de uma vez.
- Padrão de classe: omitir a classe do valor padrão do core (`md` não emite `eds-button-md`; `xl` não emite `eds-container-xl`); props sem valor não emitem classe vazia.
- Estado é atributo (`disabled`, `aria-busy`, `aria-invalid`, `aria-current`, `open`), porque é neles que o CSS do core se apoia.
- Exigência de acessibilidade vai para o tipo: `iconOnly` ⇒ `aria-label` obrigatório; `ButtonGroup` ⇒ `aria-label` ou `aria-labelledby`. Teste com `// @ts-expect-error`.
- Polimorfismo barato: `as` com união fechada de tags (`LayoutElement`) via `createElement`, só no layout. Polimorfismo de verdade (Button↔`<a>`) é por uma prop discriminante (`href`), com sobrecarga no tipo do componente.
- **Textos internos (i18n)**: sempre pela prop `texts`, um objeto **parcial** com padrões em pt-BR (`mergeTexts` em `utils/texts.ts`: chaves `undefined` não apagam o padrão), com o mesmo nome em todos os componentes (`AlertTexts`, `ModalTexts`, `ComboboxTexts`, `PaginationTexts`…). Não há props soltas de texto (nada de `*Label`, `*Message` ou `labels`/`messages`). Ficam de fora, por serem conteúdo e não texto interno: `title`, `children`, `label` do `Spinner` e do `SkeletonRegion` (diz **o que** carrega), `brandLabel` e as opções por chamada de `alert/confirm/prompt` (`okText`, `cancelText`). O idioma do `Intl` vem do `LocaleProvider` (`locale`, padrão `pt-BR`): nomes de mês e dia do DatePicker/DateRangePicker, ordem de texto de `sortTableData` (passe `useLocale()`) e datas e números do `TableExport`; a prop `locale` do componente vence. IDs com `useId`. Sem `dangerouslySetInnerHTML`. Sem efeito colateral no topo do módulo.
- Controlado e não controlado quando houver valor/abertura (`value`/`defaultValue`, `open`/`defaultOpen` + `onOpenChange`).

## Testes

Vitest + Testing Library + `user-event` + matchers do jest-dom (já no setup do preset). Seletores por `getByRole`/`getByLabelText`. Cobrir: classes por variante/tamanho, `ref`, `className` e props nativas repassados, atributos ARIA, teclado e callbacks. Visuais puros: um teste de fumaça basta. Dados fictícios.

## Verificação do pacote

`pnpm typecheck · lint · test · build · format:check`; `grep -rn "style=" packages/react/src` vazio; `dist` sem CSS; `sideEffects` correto (tree shaking).

## Notas de comportamento (Fase 6)

- **Toast sem `title`**: a severidade vai num `<span class="eds-visually-hidden">` ("Informação:", "Sucesso:", "Atenção:", "Erro:"), como em `texts.severity` do Alert. Com `title`, nada é acrescentado. A região viva é um único elemento criado uma vez e só movido (`appendChild`) entre o `body` e o `dialog:modal` aberto: não é destruída nem recriada com o toast dentro, e nunca há duas regiões. Para i18n: `<ToastProvider texts={{ severity: { danger: 'Error:' } }} />` (`severity` é `Partial<Record<ToastVariant, string>>`; `close` é o nome do botão).
- **Sidebar**: o botão de colapsar leva `aria-expanded` e `aria-controls` apontando para o `id` da `<nav>` (do consumidor, do shell no slot `sidebar` ou o gerado localmente); a `<nav>` sempre tem id.
- **Modal/Drawer (DialogBase)**: se o consumidor mantém `open` e ignora `onClose`, o dialog é reaberto 50 ms após o fechamento nativo (2º Esc). O foco volta ao último elemento focado dentro do dialog (rastreado por `focusin`), não ao botão Fechar.

## Notas de comportamento (Fase 6b)

- **Combobox**: foco sempre no `<input>` (`aria-activedescendant`); popup `popover="manual"` posicionado por `--_combobox-x/-y/-width` via `style.setProperty` (único estilo inline permitido, só posição; com `data-placement="top"`, `-y` é o `top` do campo e o CSS sobe o popup). Texto sem opção escolhida gera `setCustomValidity` (`freeText` desliga); `selectedLabel` cobre valor controlado cuja opção ainda não foi carregada; a lista é nomeada por `texts.list`/`aria-label` ou, dentro de `Field`, pelo `labelId` do contexto.
- **PageLoaderProvider**: motor sem React com `attach`/`detach` simétricos no efeito (compatível com StrictMode). `auto` (padrão ligado) faz patch de `fetch`/XHR enquanto montado e só cobre SPA (não form/link). `trigger="user"` ignora requisições sem `navigator.userActivation.isActive`. Depois de `slowAfter` (20 s) o diálogo oferece "Fechar" (libera a página e silencia as pendências até terminarem) e "Continuar aguardando". `<dialog>` fechado pelo navegador sem pedido do código é reaberto (`showModal()` no `close` enquanto `open` for verdadeiro; Chrome fecha o modal no 2º Esc).

## Notas de comportamento (Fase 6c)

- **Lógica compartilhada do Combobox**: `internal/combobox-shared.ts` (tipo `ComboboxOption`, filtro sem acento, `usePopupPosition`, `useScrollActiveIntoView`, atrasos de status) é usada por Combobox e MultiSelect. Quem novo usar o popup posiciona pelo `anchorRef` (o Combobox ancora no input; o MultiSelect, no `.eds-combobox-control`).
- **MultiSelect**: foco sempre no `<input class="eds-combobox-input">`; `aria-multiselectable`, `aria-selected` = escolhida e `data-active` = destaque. Enter/clique alterna e mantém aberto; Backspace com texto vazio remove a última; Esc fecha e, fechado, limpa só o texto. Um `hidden` por escolha (`name` usado como veio; passe `cidades[]` se o servidor espera lista). `required` vira `aria-required` + `setCustomValidity` (nunca o `required` nativo no input de texto). Status neutro em gênero ("Pelotas: selecionado. 3 itens selecionados."). O tamanho vai no controle (`.eds-combobox-control-sm|lg`).
- **FileInput**: `<input type="file" class="eds-file">`, sem JS, integra com `Field` como o Input.
- **FileUpload**: o `<input class="eds-upload-input">` fica no DOM e a dropzone é um `<label for>` (teclado nativo). Não emite `data-eds-upload` (reservado ao `@efds-ui/behavior`). Modo formulário: os arquivos válidos ficam no input via `DataTransfer` (efeito sobre a lista), então o envio normal leva tudo. Modo imediato (`upload`): o input perde o `name` e limpa o `value`; cada envio ganha `AbortController` (remover aborta), `hidden name=id` ao terminar e `setCustomValidity("Aguarde o envio dos arquivos.")` enquanto houver envio. O progresso aparece no `<progress>` mas não é anunciado. Foco após remover: próximo botão, anterior, input. Foco após "Tentar de novo" (o botão some): Remover do mesmo item. Drag só no contêiner `.eds-upload`, com contador de profundidade.

## Notas de comportamento (Fase 6d)

- **Data nativa**: `<Input type="date|time|datetime-local|month">` já serve (o core ajusta o visual); não há componente novo.
- **DatePicker / DateRangePicker**: campo de texto com máscara dd/mm/aaaa (cola dd/mm/aaaa ou aaaa-mm-dd) + botão que abre um diálogo `popover="manual"` (APG "Date Picker Dialog"), posicionado só por `--_calendar-x/-y` (com `data-placement="top"`, `-y` é o `top` do campo). Datas são locais, sem fuso (nunca `new Date('aaaa-mm-dd')`); o valor público é ISO `aaaa-mm-dd`.
- **Grade compartilhada** em `internal/` (`CalendarPanel`, `calendar-shared`, `useDateField`; não exportada). O conteúdo do diálogo só existe aberto. Roving tabindex; ←/→/↑/↓, Home/End (semana, domingo a sábado), PageUp/PageDown (mês) e Shift+PageUp/PageDown (ano, ajustando ao fim do mês); Enter/Espaço escolhe; Esc fecha, devolve o foco ao botão e dá `stopPropagation` (não fecha Modal em volta); Tab circula no diálogo; clique fora fecha; Alt+↓ no campo abre. Dia indisponível recebe foco mas não é escolhido (anuncia "Data indisponível."). Foco inicial: dia escolhido, senão hoje, ajustado a min/max.
- **Nome do dia**: `aria-label` no `td`, começando pelo número visível ("15 de março de 2026, domingo"; 2.5.3). O título do mês é `aria-live="polite"`. Dia fora do mês é `<td>` vazio.
- **Validação**: erro (data inválida, fora de min/max, bloqueada, final antes da inicial, `maxDays`) vira `setCustomValidity` sempre e `aria-invalid` + anúncio só depois do blur/Enter. O hidden (`name`, `nameStart`/`nameEnd`) recebe ISO ou fica vazio se houver erro. `required` é nativo no campo de texto. A mensagem não é desenhada pelo componente: mostre-a via `Field error` se quiser texto visível.
- **Bloqueios**: `min`/`max` (ISO), `isDateDisabled(date)`, `disableWeekends`. DateRangePicker: `maxDays` (dias corridos, início e fim contam); dias bloqueados podem ficar no meio do período, não ser início/fim.
- **DateRangePicker**: 1º dia = início, 2º = fim (anterior ao início vira o novo início); fecha após o fim. Dias do período têm `aria-selected="true"` e `data-range="start|middle|end|single"` (`single` = só o início ou início = fim); a prévia (`data-range-preview`, sem `aria-selected`) vai do início ao dia sob o ponteiro/foco. Status: "Início: dd/mm/aaaa. Escolha a data final." e "Período: dd/mm/aaaa a dd/mm/aaaa.". Dentro de `Field`, o rótulo nomeia o grupo (`aria-labelledby`) e o `id` vai ao campo inicial. O `ref` vai para o grupo; no DatePicker, para o `<input>`.
- **Textos e idioma**: `texts` (todos os rótulos e mensagens, em função quando recebem dados) e `locale` (padrão `pt-BR`, via `Intl`; a semana começa no domingo e a máscara continua dd/mm/aaaa). O tamanho (`size`) vai no input (`eds-input-sm|lg`).
- **Testes**: jsdom esconde `[popover]` fechado e não tem `showPopover`; os testes usam `installPopoverStyle()` (`test-utils/dom-polyfills.ts`) para tratar o popup como visível.

### Correções da auditoria UX (Fase 6d)

- **Erro visível**: sem erro vindo do `Field`/`invalid`, o componente renderiza `<p class="eds-error">` logo após `.eds-datepicker` e o liga ao `aria-describedby` do campo afetado (no período, um por campo). O erro do `Field` prevalece (nada duplicado). Aparece só depois de blur/Enter (no período, ao sair do grupo); o status live continua como reforço.
- **Máscara** preserva o cursor ao editar no meio (dígitos antes do cursor, restaurado em `useLayoutEffect`).
- **Período incompleto** (só início ou só fim) é erro mesmo sem `required` ("Informe também a data final." / "…inicial."; `texts.missingEnd`/`missingStart`).
- **Mensagens**: "{data}: data indisponível." (`texts.unavailable(data)`), "O período pode ter no máximo N dias.", ano de 2 dígitos pede 4 dígitos. Status ao escolher: "Data selecionada: 26 de dezembro de 2026, sábado.".
- **Calendário**: `aria-modal="true"`; prévia do período limitada a `maxDays` e min/max; entre ponteiro e foco vale o último a mudar. Alt+↓ no campo final abre no mês da data final. Nome do botão com valor ("Escolher data. Atual: 15/03/2026"; `texts.toggleWithValue`).
- **`id` explícito** num DatePicker dentro de `Field` com `controlId` diferente: o `for` do rótulo não chega ao campo, então o nome vem por `aria-labelledby` do rótulo do Field (o `Input` não faz isso).

- **Anunciador (`internal/announcer.ts`)**: o "tick" é uma microtask, igual ao `createAnnouncer` do behavior: anúncios do mesmo tick são concatenados; de ticks diferentes, cada um substitui o anterior (timers atrasados em aba de fundo não os juntam). **Tabs**: o tab stop (`tabindex=0`) nunca fica numa aba desabilitada focada por setas; fica na selecionada.

## Notas de comportamento (Fase 6e)

- **DialogProvider / useDialog**: `const { alert, confirm, prompt } = useDialog()` com as assinaturas posicionais do behavior: `alert(texto, título?, tipo?, opções?)` → `Promise<void>`; `confirm(texto, título?, tipo?, opções?)` → `Promise<boolean>`; `prompt(texto, valorPadrão?, título?, opções?)` → `Promise<string | null>`. `tipo`: `info` (padrão do alert), `success`, `warning`, `danger`, `question` (padrão do confirm e do prompt). `opções`: `okText`, `cancelText`, `placeholder`, `required`, `inputType` (`text|email|number|password|textarea`), `validate(valor) => mensagem | ''`. Fora do provider, `useDialog` lança erro.
- **Markup**: um único `<dialog class="eds-modal eds-alert-dialog" data-variant>` por vez (fila em ordem de chamada), com ícone, título (h2), texto, campo (prompt) e ações. Sem título, o texto nomeia o diálogo e não há `aria-describedby`. `role="alertdialog"` só em confirm/prompt `danger`/`warning`. Prefixo de severidade oculto ("Erro:", "Atenção:"…) antes do título (ou do texto); `question` sem prefixo.
- **Foco e teclas**: alert no OK; confirm no Cancelar se `danger`, senão no OK; prompt no campo, com o texto selecionado. Enter confirma (em `textarea`, Ctrl/Cmd+Enter); Esc, 2º Esc nativo e clique no fundo cancelam (`undefined`/`false`/`null`); `danger` ignora o fundo. Esc dá `stopPropagation` (não fecha um Modal em volta). O foco volta ao elemento ativo antes da primeira chamada da fila.
- **Prompt**: `required` ou `validate` com erro mostram `<p class="eds-error">` ligado por `aria-describedby`, `aria-invalid`, foco no campo, `role="alert"` no `<p>` (sem região de status extra); não fecha. `options.variant` no prompt (padrão `question`). O erro some ao digitar.
- **Textos**: `<DialogProvider texts={{ ok, cancel, confirm, required, severity }} />` (parciais). Desmontar o provider resolve as pendentes como canceladas. Glifos em `internal/glyphs-dialog.tsx`.

## Notas de comportamento (Fase 6e: Sortable e Tree)

- **Motor de arrasto** (`internal/drag.ts`, privado): Pointer Events com limiar de 4px, fantasma (clone com `inline-size` e `transform`, anexado ao `dialog:modal` aberto, senão ao `body`), rolagem automática perto da borda, Esc cancela com `stopPropagation` (não fecha Modal) e o `click` que encerra o arrasto é engolido. Sem a API HTML5 de Drag and Drop.
- **Sortable / SortableGroup**: `Sortable` controlado (`items` + `onChange(items, change)`); várias listas que trocam itens ficam num `SortableGroup` (`lists` + `onChange(listas, change)`), com `id` em cada `Sortable` filho. `renderItem(item, { handle, handleProps, index, listId, dragging })` (o pegador `<button class="eds-sortable-handle">` já vem pronto; `handle={false}` torna o item focável). No teclado o item se move ao vivo num rascunho e só o soltar chama `onChange`; Esc descarta. Ponteiro: o original fica esmaecido (`data-dragging`) e o `.eds-sortable-placeholder` mostra o destino (`data-drop-target` na lista). Perder o foco para fora do grupo cancela a pega. `←/→` (vertical) ou `↑/↓` (horizontal) trocam de lista; na grade as quatro setas andam ±1 (sem troca de lista). `name` gera um `hidden` por item.
- **Tree**: APG completa (roving tabindex, setas, Home/End, `*`, type-ahead sem acento, Enter ativa, Espaço seleciona, Ctrl/Shift em `multiselect`). Controlada (`items`/`onChange`) ou não (`defaultItems`); `onChange(items, { action: 'add'|'rename'|'move'|'delete'|'wrap', node, parent, index })`; `onBeforeChange` devolvendo `false` cancela. Edição (`editable`): F2/duplo clique, Insert/Ctrl+Enter (filho), Shift+Enter (irmão), Delete, Alt+setas, Shift+F10/Menu abre o menu "⋯" (Dropdown; itens só existem com o menu aberto). Exclusão com subitens usa `useDialog().confirm` se houver `DialogProvider` (via `useOptionalDialog`, interno), senão `window.confirm`. Arrasto por zonas (`data-drop="before|inside|after"` e `data-drop-invalid` no `.eds-tree-row`); soltar em si ou descendente é inválido; parado 600 ms "dentro" de nó recolhido o expande. O `li` leva `aria-label` com o rótulo (o nome por conteúdo incluiria a subárvore).
- **Alinhamento com o behavior** (mesmos textos de `config.ts`): pelo ponteiro o original leva só `data-dragging` (o CSS o esconde) e o placeholder reserva o destino desde o começo; item sem pegador usa `data-grabbed` (nunca `aria-pressed` em div/li); toque sem pegador e nas linhas da Tree exige segurar 400 ms parado (`touchHoldMs` do motor; mexer antes devolve a rolagem à página), com pegador vale o limiar de 4 px. Teclado do Sortable: Enter e Espaço pegam/soltam, Home/End, PageUp/PageDown trocam de lista, grade com ←/→ ±1 e ↑/↓ uma linha (colunas pela geometria), na ponta repete "Posição N de M.", sem lista vizinha "Não há outra lista nessa direção.".
- **Tree**: Shift+setas estendem a seleção no `multiselect` (Ctrl+Espaço alterna); `loadChildren(node)` + `hasChildren` no nó carregam ao expandir (`aria-busy` no `li`, "Carregando…", erro anunciado e nova tentativa ao reexpandir; carregado vazio vira folha). Os filhos carregados entram no `items` entregue ao `onChange`.
- **Desfazer exclusão**: com `ToastProvider` acima, excluir mostra o toast com "Desfazer" por 8 s (`ToastOptions.action` e `duration`, novos; `useOptionalToast` é interno) e restaura na mesma posição (`onChange` com `action: 'add'`). Sem provider, não há desfazer.

## Notas de comportamento (exportação de tabelas)

- **Dependência react → behavior**: `@efds-ui/react` declara `"@efds-ui/behavior": "workspace:*"` em `dependencies` e importa apenas `@efds-ui/behavior/export` (sem `init`, auto-init ou os outros módulos); o build mantém `@efds-ui/*` como `external`. No monorepo, o `tsconfig.json` do react usa `customConditions: ["development"]` para ler o código-fonte do behavior (o typecheck não exige build prévio); o `tsconfig.build.json` zera as condições e lê os `.d.ts` do `dist` (o `pnpm build` constrói o behavior antes). Os apps (docs e playground) mapeiam `@efds-ui/behavior/export` por alias, **antes** do alias de prefixo `@efds-ui/behavior`.
- **TableExport**: `Dropdown` (disclosure, `role="group"`) cujo gatilho é um `Button` com glifo de download e cujos itens são os formatos (`formats`, padrão `csv`, `xlsx`, `json`, `pdf`; rótulos em `texts.csv|xlsx|json|pdf`, botão em `texts.label`). A fonte é o estado, não o DOM: `data` ou `getData()`, lido no clique. `onBeforeExport(data, { format, filename })` devolve os dados a exportar (a fonte do consumidor não é alterada), `false` cancela sem baixar nem anunciar. `onExport({ format, filename, count })` roda depois. Sem linhas (ou `onBeforeExport` que as zera): anuncia "Não há linhas para exportar." e não baixa; erro em `getData`, no `onBeforeExport` ou na geração: "Não foi possível gerar o arquivo.". Anúncio em `<span role="status">` irmão (`useAnnouncer`), com os textos do behavior (`getMessages`, então `configure({ messages })` vale) ou os de `texts` (`done`, `doneOne`, `empty`, `failed`). `locale` (ou o do `LocaleProvider`) vai para o gerador: ordem da data, separadores e `/Lang` do PDF. O nome ganha a extensão do formato (uma extensão igual no `filename` não duplica) e **não** leva a data (diferente do HTML, que acrescenta `-aaaa-mm-dd`). O `ref` vai ao botão.
- **LGPD**: o arquivo leva o que `data` contém; mascare ou retire colunas sensíveis em `onBeforeExport` (ou, melhor, no servidor) e use o mesmo gancho para auditoria.

## Notas de comportamento (paridade com o behavior)

- **Table ordenável pronta**: `<Table sort onSortChange>` + `<TableHeaderCell sortKey>`. Com `onSortChange`, o cabeçalho deriva `aria-sort` (`none` nas outras colunas) e, ao ser acionado, pede `{ column, direction }` (primeiro crescente, depois alterna; outra coluna começa crescente), como o behavior. A Table renderiza sua região `role="status"` (irmã do wrap) e anuncia "Ordenado por X, crescente." (`texts.sortedBy`, padrões do `getMessages` do behavior). `sort`/`onSort` à mão seguem valendo; sem `onSortChange`, `sortKey` não faz nada.
- **Dados**: `sortTableData(linhas, ordem, { getValue?, locale? })` e `filterTableData(linhas, texto, { columns?, getText? })` usam as regras do behavior (`core/data.ts`, exportadas por `@efds-ui/behavior/export`): número pt-BR ou ponto decimal, data dd/mm/aaaa ou ISO, texto por `Intl.Collator` sem acento/caixa, vazios por último, estável. `useTableFilter(linhas, { columns?, getText?, delay?, texts? })` devolve `{ query, setQuery, rows, count, status, inputProps }`: atraso de 150 ms, Esc limpa e `status` ("N resultados.", "Filtro removido. N linhas.") vai em `<Table status>`, só depois de uma ação do usuário.
- **Seleção da Table**: `TableCell`/`TableHeaderCell` com `column="check"` envolvem o conteúdo num `<label class="eds-check">` (amplia o alvo do clique); o checkbox sem texto mantém o `aria-label` como nome.
- **ConfirmButton** (equivalente do `data-eds-confirm`): componente à parte, não prop do `Button`, para que o `Button` (usado em toda parte) não puxe o `Dialog` para o bundle de quem não confirma nada. Props: `confirm` (pergunta), `confirmTitle`, `confirmVariant`, `confirmOkText`; aceita `href`. Pergunta com `useDialog().confirm` e, no "sim", repete o clique: o botão `submit` envia o formulário, o link navega e o `onClick` do consumidor roda só aí. Exige `DialogProvider`.
- **readOnly**: `Select` (não existe no `<select>`: `aria-readonly`, `mousedown` e teclas de escolha barrados, segue focável e enviado), `Combobox`, `MultiSelect` (lista não abre, valor e etiquetas não mudam, `aria-readonly`), `DatePicker` e `DateRangePicker` (botão do calendário desabilitado, colagem ignorada).
- **size**: `Textarea`, `Checkbox`, `Radio`, `Switch` e `Badge` aceitam `'sm' | 'md' | 'lg'` (emitem `.eds-<comp>-sm|-lg`); `Modal` aceita `size="full"` (`.eds-modal-full`).
- **`error`**: toda prop pública `error` é `ReactNode` (Field, Fieldset, Combobox, MultiSelect). O `FileUpload` não tem prop `error`: usa `invalid` e o `error` do Field; o `string` apontado na lista de melhorias é o estado interno de cada arquivo (`texts` produz strings).

## Notas de comportamento (máscara de entrada)

- **API**: `Input` ganha `mask`, `maskOptions`, `unmask` e `onValueChange(masked, raw)`; sem `mask` o componente se comporta exatamente como antes. O núcleo vem de `@efds-ui/behavior/mask` (mesma lógica do HTML por atributos, sem `init`); o hook é `internal/useInputMask.ts`.
- **Markup**: emite `data-eds-mask="<nome ou padrão>"` (é o que o CSS do core usa para alinhar moeda e número), mais `inputmode`, `autocomplete` (telefone e CEP) e `maxlength` (nunca na moeda e no número) só quando o autor não os definiu. **Não chame `init` do behavior sobre markup do React**: o `Input` já faz a máscara.
- **Controlado e não controlado**: `value` e `defaultValue` são exibidos mascarados (aceita o valor com ou sem máscara; na moeda, também o número com ponto decimal). O `onChange` do autor recebe `event.target.value` já mascarado, então `setValue(e.target.value)` funciona. O cursor é recolocado na hora e de novo num `useLayoutEffect`.
- **Colar**: tratado em `onPaste` (sem o corte do `maxlength`); o valor entra pelo setter nativo e um evento `input` faz o React chamar `onChange`. Um `onPaste` do autor com `preventDefault` cancela a colagem.
- **`unmask`**: com `name`, o visível perde o `name` e o componente devolve um fragmento com um `<input type="hidden">` (`name`, `form` e `disabled` do campo) com o valor limpo. A `ref` continua apontando para o campo visível. Um `reset` do formulário refaz o valor limpo.
- **Limitações**: composição de IME não é mascarada até terminar; `maxlength` cheio impede inserir no meio, como em qualquer campo.

## Notas de comportamento (onda B)

- **Accordion/AccordionItem**: `<details name>`; `exclusive` gera o `name` com `useId`. `open`/`defaultOpen`/`onOpenChange` (o `toggle` nativo é a fonte da verdade, então o fechamento por outro item do grupo também avisa). `disabled` = `aria-disabled` no `<summary>` + `preventDefault` no clique.
- **Tooltip**: renderiza o gatilho clonado (`aria-describedby`, `data-eds-tooltip="<lado>"`) e, logo depois, o `.eds-tooltip[popover=manual]`; um efeito chama o `tooltipBehavior.bind` do `@efds-ui/behavior/balloon` no `previousElementSibling` (mesmo código do HTML: atraso, Esc, pairável, posição). O gatilho precisa repassar `aria-describedby` e `data-*` ao DOM.
- **Popover**: gatilho clonado (`popoverTarget`, `aria-expanded`, `data-eds-popover="<lado>"`), painel `popover="auto"` logo depois, `popoverBehavior.bind` no efeito. O tipo exige `title` **ou** `aria-label`. `actions` aceita função `({ popoverId }) => ReactNode` (botão Fechar nativo). `open` controlado usa `showPopover`/`hidePopover`; `onOpenChange` vem do `toggle`. Não chame `init` sobre ele.
- **Validação (ErrorSummary, useFormValidation, `Input validate`)**: regras e textos vêm de `@efds-ui/behavior/validate` (nenhuma duplicada). `Input validate` só liga `setCustomValidity` (efeito + ouvintes `input`/`change`); o erro visível é do `Field error={errorOf(name)}`. `useFormValidation` lê a validade nativa dos controles do `<form>` (não guarda valores, funciona com campos controlados ou não): `formProps` (`noValidate`, `ref`, envio, `onBlur`, `onInput`/`onChange`, `pointerdown` em botão), `errorOf`, `summaryProps` e `validate()`; mesmas regras de exibição do HTML (primeiro erro ao sair do campo ou enviar; depois acompanha; resumo só perde itens ao corrigir). `ErrorSummary` não emite `data-eds-error-summary` (o behavior não pode ligar no markup do React); foca por `focusKey` (ou ao passar de zero a algum erro), nunca na primeira renderização; região de status própria avisa quando zera.
- **Stepper/Wizard**: `Stepper` deriva estados de `current` (`steps[i].state` sobrescreve), marcador vazio (CSS), `.eds-stepper-summary` só no item atual, `onStepClick` troca o rótulo concluído por `<button class="eds-stepper-label">`. `Wizard` (form `noValidate`) mantém todos os painéis montados, valida o painel nativamente (`validate` extra), foca o `<h3>` da etapa nova, anuncia por `useAnnouncer`, "Avançar" é `type=submit` (Enter avança) e "Concluir" na última; `onComplete(FormData)` impede o envio nativo. Um painel anterior inválido no envio final reabre e vira `error`.
- **Stat/StatGrid**: `.eds-card.eds-stat` + `data-trend`/`data-tone`, seta svg desenhada para cima, direção em texto oculto (`texts.up/down/flat`), `loading` com Skeleton + `role=status`. Sem prop `icon` (o CSS tem `.eds-stat-icon`, mas a API fica mínima).
- **FilterBar**: controlado (`active` com `onRemove`, `onSubmit`, `onClear`); `more` + `moreCount` montam o `<details>` "Mais filtros" com contador; depois de remover um chip o foco vai ao próximo chip ou ao primeiro campo. O `reset` nativo dispara `onClear`; `submit` é sempre impedido.
- **Page/PageHeader/PageToolbar/PageBody/PageFooter**: só classes `.eds-page-*`; `sticky` documenta o risco de 2.4.11 (`scroll-padding-block-start` é do consumidor). As telas de referência do playground usam `PageHeader` (todas), `FilterBar` (Listagem) e `StatGrid` (Dashboard).
- **Table `loading`**: `aria-busy` na tabela + região `role=status` presente desde que `loading` é definida (texto só ao carregar, `texts.loading`); `loadingOverlay` acrescenta `.eds-table-overlay` com Spinner; `TableLoadingRows` emite `tr.eds-table-loading` com Skeleton. Corpo de Modal/Drawer rolável focável já vinha de `useScrollRegion` (onda A).

## Table avançada (contrato em `table-avancada.md`)

Reordenar, ocultar, filtrar e editar são **re-renderização**: o React não mexe na ordem do DOM como o behavior; o markup emitido é o mesmo do HTML (`.eds-table-th`, `.eds-table-sort-order`, `.eds-table-filter-btn`, `.eds-table-filter`, `.eds-table-colhandle`, `.eds-table-resize`, `.eds-table-bulk*`, `.eds-table-cell-edit`, `td[data-editing]`). Os anúncios saem pela região `role="status"` da `<Table>` (um por ação); a barra de lote tem a sua, fora do grupo escondido.

- **Ordenação múltipla**: `<Table multiSort sortMax sort={TableSortState[]} onSortChange>` (`multiSort`: `true`/`'shift'` = clique substitui e Shift+clique/Shift+Enter/Shift+Espaço acrescenta; `'add'` = todo clique acrescenta). União discriminada no tipo: sem `multiSort`, `sort`/`onSortChange` seguem de uma coluna só (sem quebra). `aria-sort` só no critério primário; secundários levam `data-eds-sort-dir`/`-order`, o número `.eds-table-sort-order` e o texto oculto `, critério 2, decrescente`; a dica de Shift (`texts.sortHint`) liga por `aria-describedby`. `texts`: `sortedByMany`, `sortRemoved`, `sortMaxReached`, `sortOrderLabel`, `sortHint`. `sortTableData` aceita um critério ou uma lista (usa `sortByCriteria`).
- **Filtro por coluna**: `<TableHeaderCell filter={<TableColumnFilter type value onChange options multiple label texts />}>`. `type`: `text` (contém), `select` (`string[]`; `multiple` = caixas), `number` e `date` (faixa `{ gte, lte }`, erro em `p.eds-error` se invertida). Painel = `Popover` nativo; Enter/"Aplicar" aplica, "Limpar" zera, Esc fecha e os campos voltam ao aplicado; o botão leva `data-active` e o nome ", filtro ativo". `filterTableData(linhas, texto, { filters, getValue })` aplica os filtros em E com a busca (`matchColumnFilter`). Não há componente de chips no React (o app compõe com `Chip`).
- **Colunas**: `useTableColumns(defs, { prefsKey?, state?, onStateChange? })` devolve `columns` (visíveis, na ordem), `all`, `state`, `move`, `resize`, `toggle`, `reset`, `setState`, `canHide`, `position`, `announce`. Passe-o a `<Table columnsController reorderable resizable>` (renderiza `<colgroup>`, `eds-table-fixed`, `--_pin-inset`/`--_pin-start-size`/`--_pin-end-size` e `data-pin-disabled` por efeito) e mapeie `controller.columns` nos `<TableHeaderCell columnId>`/`<TableCell columnId>` (fixação por `pin` na definição; `locked` não move, não oculta, não redimensiona). Alça `.eds-table-colhandle` com o teclado da seção 5.2; arrastar a alça reordena e arrastar `.eds-table-resize` redimensiona (duplo clique volta ao automático). `<TableColumnsMenu controller reorderable resizable texts />` é o painel (alternativa a arrasto, WCAG 2.5.7). Preferências: `localStorage` `eds:table:<prefsKey>` com `{ v: 1, order, hidden, widths }` (mesmo formato do HTML; ordenação e filtros não são salvos). **Exceção documentada a "sem estilo no React"**: a largura em px do `<col>` (dado do usuário) e as variáveis `--_pin-*`.
- **Lote**: `<TableBulkBar count total scope onClear onSelectAllResults returnFocusTo texts>` com as ações como `children`; sempre montada (`hidden` com `count === 0`); ao se esconder com o foco dentro devolve o foco (`returnFocusTo`, o "selecionar todos" ou o wrap). A seleção entre páginas é do app.
- **Tabela remota**: `useTableQuery({ initial?, syncUrl?: false | 'search', params? })` devolve `{ query, setSort, setSortState, sortState, setPage, setSize, setFilter, setQ, clearFilters, reset, searchParams }` no mesmo formato de URL do HTML (`parseTableQuery`/`toTableSearchParams`). Sem `fetch`: o app usa `query`/`searchParams` e passa `loading`/`loadingOverlay`/`status` à `<Table>`. Mudar ordenação, filtro, busca ou tamanho volta à página 1; `syncUrl: 'search'` lê a URL ao montar e usa `replaceState` (e `pushState` na troca de página).
- **Edição na célula**: `<TableEditableCell field value display? type editor columnLabel rowLabel required validate format onCommit texts />` (é o próprio `<td>`). Botão com o texto visível no nome; Enter/Espaço/F2/clique abrem; Enter confirma, Esc cancela, Tab válido confirma, inválido mantém a edição com `p.eds-error`. `onCommit` sem promise é otimista; com promise a célula fica `aria-busy` e o editor `readOnly`; rejeitar com `Error(mensagem)` volta à edição com o erro. Divergência do contrato: `columnLabel` e `rowLabel` são props obrigatórias (o React não lê o cabeçalho do DOM).
- **Migração**: sem quebra obrigatória. `sortTableData` aceita lista; `filterTableData` ganhou `filters`/`getValue`; `TableTexts` ganhou chaves novas; `Table` e `TableHeaderCell` ganharam props opcionais.

## Padrões do template ERP

- `OptionCard` (`type`, `title`, `description?`, `mark?`; `ref`/`className`/props nativas vão ao `<input>`, filho direto do `<label class="eds-option-card">`) e `OptionCardGroup` (= `RadioGroup` com a grade `.eds-option-cards`: `name`, `value`/`onValueChange` controlam os rádios; `error` do grupo marca cada cartão `aria-invalid`).
- `IconDisc` (`tone`, `size`, `round`): decorativo (`aria-hidden`), tom em `data-tone` (`accent` é o padrão e não emite atributo).
- `Timeline`: `orientation="horizontal"` (classe `.eds-timeline-horizontal`; emite `tabIndex={0}` e `aria-label` = o do autor ou `texts.label`, para rolar pelo teclado) e `state` por item (`data-state`, vale também na vertical).
- `Stepper` em modo indicador: qualquer `steps[i].href` troca o rótulo por `a.eds-stepper-link` (o `aria-current` vai no link, não no `li`) e o clique leva o foco ao título da seção; `state` aceita `done`. `useSectionProgress(sections)` devolve `{ current, states }` (IntersectionObserver, `hashchange` e `input`/`change` do documento; anuncia "Seção X concluída." uma vez pela região global). A regra de "seção concluída" é a mesma do behavior (`internal/sections.ts`, duplicada de propósito: o React não depende do behavior para isso).
- `Lookup`: `autocomplete` (padrão `true`; o campo passa a `role="combobox"`, o que muda os testes que buscavam `textbox`), `onCreate(text)`, `createAlways`, `texts.create`. Usa `usePopupPosition` do Combobox (que agora limita o x à janela).
